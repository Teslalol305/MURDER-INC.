# The Unreal box: how to work on it

The rented Linux GPU box (RTX PRO 6000, 16 cores, 64 GB) runs Unreal Engine 5.9.0 (preview 2, changelist 60738873).
It costs about 114 credits per hour while it runs: keep the loop short, stop the editor when done.
Every script below lives in `tools/box/` and is mirrored on the box at `/project/ue/repo/tools/box/`.

## 1. Facts of the box

| Fact | Consequence |
|---|---|
| `/project` is persistent storage on a 9p network file system; everything else is lost when the box stops | The engine (`/project/ue/UnrealEngine`), the repository mirror (`/project/ue/repo`), the cache (`/project/ue/ddc`), the logs (`/project/ue/logs`) and the received art (`/project/ue/art-in`) live there. Never run recursive `du`/`find` over the engine: minutes. |
| The engine, the build tools and git on the mirror refuse root | Every script re-executes itself as user `ue4` (`mi_become_ue4` in `lib.sh`). After a box restart run `/project/ue/setup-box.sh` (re-creates `ue4` and the system packages; `/project/ue/logs/setup.log` ends with `SETUP-DONE`). |
| One command per MCP call, 45 s at most | Anything longer is started detached (`setsid nohup ... &`) and polled: `build.sh`/`build-status.sh`, `test.sh`/`test.sh status`, `block.sh start`/`block.sh wait`. Never `pkill -f`/`pgrep -f` (they match the calling shell): `pkill -x UnrealEditor`, `CrashReportClie`, `ShaderCompileWo` (names cut to 15 characters). |
| The stock Zen local cache cannot be reached | Every editor or `UnrealEditor-Cmd` start passes the file-system cache graph and turns Zen auto-launch off: `-DDC=(ProjectPak,InstalledProjectPak,EnginePak=InstalledEnginePak,EnterprisePak,InstalledLocal) -ini:Engine:[Zen]:AutoLaunch=false` plus `UE-LocalDataCachePath=/project/ue/ddc` (`MI_CACHE_ARGS` in `lib.sh`, `/project/ue/bin/run-editor.sh`). |
| Windows abort the editor (Vulkan bridge PrimusVK) | Headless only: `-RenderOffscreen -unattended -nosplash -NoSound` (`editor.sh`). Pictures come from scene captures (`shot.sh`). |
| The packaged game (and `UnrealEditor <project> -game`) does draw in a window on the desktop rental: `desktop-run --vulkan` sets up primus_vk (render on the card, present through llvmpipe) | The demo runs that way at 60 fps (`tools/box/demo/start.sh`, `docs/DEMO.md`); pictures of the desktop with PIL `ImageGrab.grab(xdisplay=":1")` (`/opt/venv/bin/python3`), input with `xdotool`. |
| The Unreal Build Accelerator asserts on the 9p volume (`rename-while-open ... .gch.tmp`) | `build.sh` always passes `-NoUBA`. |
| The asset registry watches every directory of `Engine/Plugins` (55,000 on 9p: 10 to 25 minutes per editor start) | `-ini:Engine:[ConsoleVariables]:AssetRegistry.DisableDirectoryWatcher=1` on every editor process (`MI_EDITOR_ARGS`). Files copied into `Content/` while the editor runs are not seen until a restart or `scan_paths_synchronous`. |
| Scene captures get no real-time sky light (`ReflectionEnvironmentRealTimeCapture.cpp` skips scene-capture views) and no Lumen lighting here: every shade is black, whatever the frame count. The headless level viewport is a main view, but it only draws when asked | `shot.sh ... cam=...` pilots the level editor viewport with a transient camera actor (position, rotation, field of view), forces `frames` redraws through the MCP tool `CaptureEditorViewport` so Lumen, the sky capture, auto exposure and TSR settle, then takes `HighResShot <size>` (written on a later redraw, after `r.HighResScreenshotDelay`). The old scene-capture path stays as `view=capture`. |
| Physically based daylight overflows the default cached-lighting range: "Cached lighting in Lumen and real-time sky capture lighting is going to be clipped" on screen, and darker shade | `r.EyeAdaptation.CachedLightingPreExposure=8` in `Config/DefaultEngine.ini` `[SystemSettings]` (covers EV -4 to 16). |
| Deleting a material that instances use orphans them; each orphan then compiles the default material synchronously on the game thread | `build_block.py` rebuilds the master material and its instances in place, never deletes them. |
| Hardware ray tracing works on this driver (NVIDIA 620.70, Vulkan) | `vulkaninfo` lists `VK_KHR_ray_tracing_pipeline`, `VK_KHR_acceleration_structure`, `VK_KHR_ray_query` on the RTX PRO 6000; editor.log: "Ray tracing is enabled", "Ray tracing shaders are enabled", and the ray-tracing scene buffer is allocated. `Config/DefaultEngine.ini` keeps `r.RayTracing=True` and `r.Lumen.HardwareRayTracing=True`. |
| The first editor start on a fresh box takes about 10 minutes (9p reads, shader maps), later ones about 40 s | Start the editor first, do the local work while it comes up; `editor.sh status` says when MCP answers. |
| Editor tools refuse to run while the editor compiles shaders ("running a slow task") | Retry `block.sh start` / `shot.sh` after a few seconds; the first pictures after a material rebuild wait for the compile. |
| A freshly rented box reads `/project` cold: UBT's first makefile scan of the engine's plugin folders took 20+ minutes (2026-11-24, box ec087d85), the editor's first start 10 minutes, and the file-system cache's maintainer (it scans the whole shared cache at start) starved the cooker's own cache reads ("is very slow (0.00 MiB/s)") | Be patient with the first build; the cloud package passes `-NoDDCCleanup` to the cook (`package-cloud.sh`). Never `pkill -f` a pattern that also appears in your own command line: it kills the calling shell |
| A command killed by the MCP call's time limit leaves its children running (parent PID 1): a `find /` and a recursive `grep` over the engine source kept the 9p volume so busy that a Node signalling server sat at 100 % CPU for 5 minutes without listening (2026-11-24) | Start long scans detached with a `timeout`, look for leftovers (`ps -eo pid,ppid,etimes,args`) before blaming a slow box |
| WebRTC on box ec087d85: the game's WebRTC stack gathers host candidates (172.20.x), headless Chrome gathers none (gVisor sandbox; its IP-handling and loopback flags change nothing) | A browser cannot be the viewer here; a Python aiortc client can (`/project/ue/cloud/verify-v2/rtcview.py`: real H.264 frames and Opus from the cloud build). Input, gamepad and the browser side stay untested on the box |
| Input through a stream can be tested on the box without a browser: `tools/box/cloud/rtcinput.py <streamerId> <script>` (aiortc, in `/tmp/fps/venv`; put the venv back with `pip install aiortc websockets pillow` if `/tmp` was wiped) subscribes through the signalling server (`e3ds-repro.sh ss start`), receives the video and sends mouse, keys, gamepad buttons and axes and console commands over the data channel in the browser player's own message formats | Start the game with `-MICloudProbe=0.25`: each probe line has `yaw= pitch= state= click= viewers= spikes= pad= cmdRun= cmdRefused= padRepeats= stickKeys=`, so a script line can be matched to what the game did. `frame x.jpg` saves a received frame. Limits read from Pixel Streaming's protocol: one mouse event beyond half the player's width wraps in its 16-bit field; triggers come as axes only; a held button is sent again every frame as a repeat. |
| The game deletes a `Saved/Config/Linux/*.ini` it did not write when it exits, and a Saved folder keeps settings between runs (`SaveGames`: a sensitivity changed in one stream test scaled the next test's turn) | A test that needs an ini override writes it before every run (or uses `-ini:`); a test that measures look speed deletes `Saved/SaveGames` first. |
| Two or three games on the one GPU (several agents testing streams at once, 2026-11-24 23:30) make each of them GPU-bound: Pixel Streaming skips captures ("No frames available for capture"), a viewer receives black or stale frames and the game's frame rate drops to 20 to 45 | Look at `nvidia-smi` before a stream test and do not read frame rates, delays or pictures from a run that shared the GPU; the same test alone on the GPU had 60 frames a second and no skipped capture. |
| A game that renders off screen never waits for the GPU (no display to present to: Unreal's Vulkan viewport returns before its end-of-frame wait), so a game on a GPU slower than its frame rate hands it more frames than it finishes; the unfinished frames pile up (79 were counted), memory grows with them (3.3 GB to 14.5 GB in 40 s, box run `gp-in5`), and the next wait for a GPU result (the occlusion read-back when the view stops turning, Pixel Streaming's capture fence, the shutdown) lasts as long as the pile: frames of 1 to 8 s. This was the lag of version 2 on E3DS | Version 3's pacer (`Source/MurderInc/Cloud/MIPacing.h`, `MI.Cloud.GpuFramesInFlight`). When a streamed game stalls for seconds, read `owed=` in its probe lines first: it is the number of frames the GPU still owed at the start of a frame |
| Lag tests: `tools/box/cloud/lag-test.sh` runs one game at a time (it waits for a free GPU and a watcher notes any other game: the summary says CLEAN or POLLUTED), with a calibrated GPU load from a second process (`gpu_hog.py`: the driver gives the two processes turns, so the game's frames take longer whatever it draws), a viewer that stands, turns slowly, turns fast and walks, and one summary line per run (`lag_sum.py`); `lag-test.sh queue <file>` runs a list (`lag-gate.txt` is the release gate) | Loads on box ec087d85 (GPU time of a frame of the Story run at full quality, 1080p): none 6.3 ms, `1:0.3:1` 8.1 ms, `1:0.05:0.05:1024` 11.4 ms, `1:0.05:0:1024` 19.3 ms, `1:0.3:0` 33.8 ms, `1:1:0` 48 ms, `1:4:0` 143 ms; calibrate again on another card (`lag-test.sh calib`). No compile while a run measures |
| The Python viewers (`rtcview.py`, `rtcinput.py`) give the sender weak congestion feedback: it believes the connection carries 0.25 to a few Mbit/s, and WebRTC then drops most frames to fit (run `x1`, free GPU: 60 frames captured a second, 2 to 58 encoded) | Not the game. `lag-test.sh` keeps the bitrate up (`minbit=`, 12 Mbit/s: `-PixelStreamingWebRTCMinBitrate=` and `StartBitrate=`); judge the game by its probe lines and the sender's own statistics (`capFps=`, `encFps=`, `txFps=`, `availMbps=` in the probe line) |
| `-PixelStreamingLogStats` on the command line logs nothing: the plugin starts its stats logger only when the variable changes after start-up | In the Development game `con PixelStreaming2.LogStats 1` from a MIDemo script does it (hundreds of lines a second: capture timings of every frame). Version 3's probe line carries the sender's statistics by itself, in Shipping too |
| One MCP exec call ends after 60 s whatever `timeout_s` says | Sleep 45 s at most in a call; long work detached, polled |
| 3840 x 2160 output through the stream: the encoder made 46 frames a second on a free GPU, the game missed that its viewer had left and did not shut down within 30 s of SIGTERM (lag run `d7`; 2560 x 1440 was clean) | Test at 1920 x 1080 until the game limits its own size (PREFLIGHT V3-6); a 4K run that "hangs in shutdown" is this, not the game's code under test |
| A queue file that `lag-test.sh queue` is reading can still be changed: bash reads it line by line | Add lines at the end; to skip a line, overwrite its first character with `#` in place (same length, same file), never with an editor that writes a new file |
| The game's own output echoes its command line, which contains `-MICloudProbe=<seconds>` | A probe line is `MICloudProbe fps=...`: look for that, not for the bare word |
| Unreal's Vulkan RHI starts its interrupt and submission threads only with more than 6 task-graph workers (`VulkanSubmission.cpp`, `InitializeSubmissionPipe`); workers are logical CPUs minus 2 with hyper-threading, cores minus 1 without (`UnixPlatformMisc.cpp`), counted from the CPUs the process may run on. The box has 16; a small cloud GPU server with 8 hyper-threaded CPUs has 6 workers and no such threads. Finished GPU work is then noticed only when the RHI thread submits or when the render thread waits (`FRHIGPUFence::Wait`): polling a fence from the game thread saw nothing, and version 3's pacer froze for its 250 ms limit in every frame the GPU was the limit (runs `rf-cpu6-l20`, `rf-cpu6-l35`) | `lag-test.sh cpus=0-5` runs the game on 6 CPUs (`taskset`): every pacing change must pass the gate's `gate-cpu6-*` lines too. Never block on `FRHIGPUFence::Poll` in a loop (the engine's header says so); wait on the render thread. The game's `[MICloud] CPUs:` start line and the launcher's `CPUs:` line say which case a server is |
| A summary line of `lag-test.sh` judges the play only (`state=2`, viewer clicked). The set-up screens draw at 60 whatever the GPU does, so a pacing fault can sit there while the play looks clean (run `rf-cpu6-l20`: every time-out on the home screen) | Read "whole run: pacer time-outs" in the summary line as well |
| The stream's sender encodes and sends 56 to 57 of the game's 60 frames a second on a free GPU on this box (single seconds at 45 to 50; at 45 it sends 43 to 44, at 30 all 30), and nothing tried changes it: a frame cap of 120 (`rf-fps120`), a viewer that does not decode (`rf-nodec`), the encoder's LOW_QUALITY preset (`rf-lowq`), every capture setting (runs `c0` to `c7`). The loss follows the encoder's time per frame (8 ms on average, seconds of 13 to 15 ms): a frame that arrives while the frame before is still being encoded is dropped | Not the viewer, not the connection. Do not chase it with capture settings; judge a change by `encFps` in the probe lines against these numbers |
| `PixelStreaming2.WebRTC.Fps` does nothing on a running stream when the capture is coupled to the game's frames: Pixel Streaming reads it once, when a viewer's video is set up, as the most frames a second it may send (`EpicRtcStreamer.cpp`, `_maxFrameRate`), and otherwise only for the pace of its decoupled capture thread | Set it at start (`-MICVars=` or a launch option) if it must differ |
| For this game on the box's card a smaller picture saves little: 6.39 ms of GPU time a frame at a 75 % screen percentage, 6.00 ms at 50 % (runs `rf-sp75`, `rf-sp50`; 29 ms at 400 %): seven eighths of a frame do not depend on the picture's size | Dynamic resolution between 50 and 75 % is a weak lever here; the frame-rate target (and, in release B, the quality steps) carry the load |
| Input checks through the stream: `lag-test.sh game=ship view=lag-input.txt view2=lag-input2.txt probe=0.25` (mouse and keys: a double click as E3DS's page sends it, size requests, a viewer who leaves holding W and the mouse button, and what the next viewer finds) and `view=lag-pad.txt` (a controller's first press marked as a repeat, a viewer who leaves with the trigger pulled) | `python3 lag_story.py <run folder>` prints one line whenever something the probe lines report changes (`mag=`, `fire=`, `moveY=`, `outW=`, `mouseScale=`, `dbl=` ...): the run reads as a story |
| A packaged build starts its Development game only with `-MIDev=<key>` (the word in `MIDEV.key` at the package root; `MurderInc.sh`) | `e3ds-repro.sh` turns a plain `-MIDev` into the keyed form when the build folder has the file, so `lag-test.sh game=dev` and `e3ds-verify.sh` work on both kinds of folder |
| A user with a new, empty home has no graphics-driver shader cache (NVIDIA keeps it under the home), and the engine's own pipeline cache file is off in the cloud build ("Vulkan PSO Precaching = 1, PipelineFileCache = 0"), so a folder's `Saved` carries nothing either. Such a cold run (`lag-test.sh runas=fresh clean=1`: what a host that starts every session on a new machine gives) differs from a warm one in the same three places every time: the game's first frame takes 3 to 4.5 s instead of 0.3 s (2 or 3 pacer time-outs, nobody connected yet), the first set-up screen (Crew) costs one frame of about 0.85 s with one pacer time-out and, in the Development game's log, two "Timed out waiting for fence" lines, and a run that a script starts 12 s after the process logs one fence line 13 s in on 6 CPUs (a 50 ms frame). The play is the same cold and warm (version 3a's gate, PROGRESS.md) | Run the gate on a package cold, and read "whole run: pacer time-outs" as 3 there (`lag_sum.py` prints them apart: "outside the play"). A warm number says nothing about a host's first minute; `ue4`'s home on the box is warm for binaries it has run |
| `lag-test.sh`'s viewer of the Shipping game joined about 55 s after the game's first probe line until 2026-11-25 (its wait looked for a line that never comes and ran its full 60 s): every earlier run's home screen had warmed up for a minute | That is still the default, so runs compare; `join=3` is a viewer who is there as soon as the game is (the run then starts 22 to 27 s after the game) |
| The Development game has the engine's log (fence time-outs, skipped captures), but `lag-test.sh game=dev` starts its run by script 12 s after the process, which no player can do | For the log of a run as a player reaches it: `lag-test.sh run <name> game=ship <load> -- -MIDev` (the launcher starts the Development game, the viewer clicks through the screens as for the Shipping game) |
| A presigned upload address is about 1,800 characters: too long to retype into a box command without a slip | Stage it: ask `media_upload` for the files and for one small `.txt`, write the addresses into that text file locally (read them from the tool's result with a script, not by hand), PUT and confirm it, and let the box fetch it by its short address and PUT each file (`/project/ue/cloud/v3a/put.sh` on the box does that for a list). One text file per batch: an address can be written to once |
| Version 2's probe line has no `viewers=` field, and `lag_sum.py` counted no play in a run of version 2's zip ("play 0 s: fps n/a") until 2026-11-25 | Fixed in `lag_sum.py` (a line without the field counts). A control run of version 2 beside a new build is one queue line, `<name> game=dev load=1:0.3:0 build=<version 2 unpacked>` (its zip is kept as `/project/ue/cloud/v2-ceaf828d.zip`): under that load version 2 shows frames of 0.3 to 1.3 s, 498 fence lines and 2,282 skipped captures in two minutes, and does not stop on SIGTERM (run `chk-v2-l35dev` of the release check) |
| The outside load (`gpu_hog.py`) slows the stream's encoder as well as the game: its time for a frame rises from 8.5 ms to 10 to 14 ms on average, with seconds of 22 to 40 ms, and the frame behind a long encode is dropped (run `chk-l20`: 24 to 36 of 45 frames sent for six seconds of a fast turn while the game drew a steady 45) | Under a load, only the game's own lines are a measure. What the stream sends there is not what a slow card would send: on a slow card the game is the only load |
| `lag-story.txt` turns without ever stopping; version 2's freeze came when a turn ended | `lag-stops.txt` (the release check's viewer): faster turns, eight flicks of 180 degrees with dead stops between them, walking, the fire button held while turning, a reload; about 6,000 degrees in a minute. `lag-test.sh run <name> game=ship view=lag-stops.txt join=3 ...` |
| A session the way E3DS starts one, without the test tools (the release check of version 3a) | On the box: `/project/ue/cloud/chk/first-run.sh <name> <unpacked folder> <user> <seconds> <viewer script>`: a user of its own (`useradd -m` first), `env -i`, the working directory `/`, E3DS's documented arguments and nothing else, a viewer, then SIGTERM to every process of that user in the same moment (the hardest stop for the launcher: it must not pass a second signal on). `chk/two.sh` runs two copies at once with a viewer each; `chk/chk_probe.py` reads a run's raw probe lines without `lag_sum.py`; `chk/rtcaudio.py` is the viewer with a loudness reading of the received sound (the viewer's Python has no numpy: `memoryview(frame.planes[0]).cast('h')`) |
| The card's own counter (`nvidia-smi`, the watcher's `mem=`) for one game alone at 1920 x 1080 on this box: 6.1 to 6.8 GB through a Story run, 7.2 GB for about 20 s when the set-up screens are passed in six seconds; the load process adds 0.65 GB | E3DS asks an app for 4 to 6 GB on its 12 to 16 GB cards: say the number with the counter it came from (the game's own Vulkan count is about 2 GB lower) |
| Nobody on the box has ears: sound through a stream is proven by measurement (version 3b). `tools/box/cloud/rtcaudio.py` is `rtcinput.py`'s viewer with a recorder: it writes what it receives to `sound.wav` (placed by the RTP timestamps, so a lost packet is a hole of the right length), prints loudness, peak, clipped samples, digital silence and lost sound per half second, counts drop-outs, and keeps the arrival time of every sound packet and the time of every script line in `sound.wav.json`. `audio_find.py` says whether, where and how strongly a sample of `Content/Audio` is in a recording (a matched filter at the speeds the game's pitch jitter gives; what chance scores is measured with the sample played backwards and at speeds the game does not use). `sound_table.py` reads the Development game's log (`-LogCmds="LogMIAudioHost Verbose"`: one "play <file> ..." line per started sound) against the recording | `lag-test.sh run <name> ... audio=1` records; `demo=<file>` gives the Development game a script of its demo director (`sound-demo.txt`, `sound-dead.txt`); `env=A=b,C=d` adds variables to the launcher's environment; `sound-gate.txt` is the whole sound proof of a package as a queue. The instrument checks itself without the game: `rtcaudio.py --selftest <folder>` in the viewer's Python, then `audio_find.py <folder>/selftest.wav --truth <folder>/selftest-truth.json` in `/opt/venv/bin/python3` (the viewer's venv has no numpy). A packet count is not a sound: versions 1 to 3a sent 50 packets of 3 bytes a second |
| The finder's limits: a sample that is only a tone (the ear ring, a far siren) or only a short low thump (the hurt, the heartbeat: 98 % of their energy under 150 Hz) cannot be told from chance; far 3D sounds under gunfire are too quiet. "NOT FOUND" for those is not "not played" | For them, look at the band's level at the time the log gives (the hurt: 40 to 120 Hz rises by 5 to 7.5 dB in the 0.3 s after each start; the ear ring: 4.0 to 4.35 kHz rises by 11 dB). For music and other long sounds played at their own speed use a long template: `--rates 1 --chunk 3` |
| Analysis while a run measures: numpy takes every core. A run during `sound-keys-check.sh` showed 44 frames a second (lowest second 24) and a worst frame of 83 ms on a free GPU (`snd-env-alsa`) | Analyse after the run, or with `nice` on a run that only asks whether there is sound |
| The game's sound device: with `-RenderOffScreen` (the launcher always passes it) Unreal asks SDL for its "dummy" audio driver (`LinuxPlatformApplicationMisc.cpp`, `ApplySDLAudioDriverHint`), unless `SDL_AUDIODRIVER` or `SDL_AUDIO_DRIVER` is in the environment. The log: "Initialized SDL using dummy platform API backend", "Using Audio Hardware Device System audio playback device", 6 channels at 48 kHz, buffers of 1,024 frames. The box has no sound card (no `/dev/snd`); root's PulseAudio is never asked. With `SDL_AUDIODRIVER=alsa` in the environment: "ALSA: Couldn't open audio device", "Main audio device could not be initialized", no sound is started (`sndNoDevice` counts up in the probe line) and the stream carries no sound at all (run `snd-env-alsa`) | `MurderInc.sh` sets both variables to `dummy` (version 3b). Unreal's own null device, which keeps real time exactly, cannot be chosen: `FMixerPlatformSDL::OpenAudioStream` returns false when SDL lists no device |
| SDL's dummy device waits 21 ms (whole milliseconds) for every buffer of 1,024 frames (21.33 ms of sound): the mixer runs 1.1 % fast, and the stream carries 1.011 s of sound per second of wall clock (every run; a browser's player absorbs a sender's clock drift). Asked for buffers of 960 frames (`SDL_AUDIO_DEVICE_SAMPLE_FRAMES=960`: exactly 20 ms) the device runs slower than real time by its sleep's overshoot, and the stream then has holes: 20 drop-outs of up to 40 ms and 610 ms lost in 65 s (run `snd-env-960`) | Leave the buffer size alone; the launcher clears that variable. "Too fast" has no holes, "too slow" has |
| Unreal reads a Sound Wave's audio from the pak the first time it plays: the packet with the first round of each gun sample arrived 140 to 166 ms after the fire input, every later round after about 30 to 50 ms (runs `snd-dev1`, `snd-keys1`) | `UMIAudioSubsystem::Preload` loads every wave and keeps its audio in memory when a world begins play. A delay measured on a sample's first play of a session says nothing about the delay in play |
| A mono sound played 2D arrives in the stream 5 to 6 dB under what the game's own numbers (volume x category gain) say, each one the same; the stereo street bed about 2.5 dB under | Unreal's convention for a mono 2D source on its 5.1 mix, measured, not changed: levels between mono sounds are as the data gives them, the bed sits about 3 dB higher against them |
| One MCP exec call is cut at 60 s whatever it was asked: `sleep 42` and then a wait of up to 20 s came back as "timed out" (the command went on) | Keep a call's own waiting under 55 s |
| Files reach the box only through git (the box pulls the public repository, it cannot push) and through the user's Higgsfield storage | Commit and push locally, then `sync.sh` on the box. Big binary inputs (the Blender art) go through storage (section 4). |

## 2. The loop

| Step | Command on the box (`cd /project/ue/repo/tools/box`) | Time measured |
|---|---|---|
| Pull the branch | `bash sync.sh` (says `next: build.sh` when C++ changed) | 2 to 5 s |
| Build the editor target | `bash build.sh` then poll `bash build-status.sh` (`-w` for warnings) | 127 s for the game module after a C++ change; stops a running editor first |
| Tests | `bash test.sh` (all `MurderInc.*`, headless `-NullRHI` in `UnrealEditor-Cmd`), poll `bash test.sh status` | 33 s for the two current tests |
| Editor | `bash editor.sh start [/Game/Maps/L_Block]`, `status`, `stop`, `restart` | MCP answers about 40 s after start |
| Run editor Python | `python3 mi_mcp.py py <file.py or ->` (value of the last expression) | under 45 s per call |
| Build the block | `bash block.sh start [steps] [force]`, `bash block.sh wait` | textures + meshes 138 s (277 textures, 190 GLBs with Nanite), materials 65 to 96 s with force (6 masters, 160 instances; shaders compile afterwards for a minute or two), level 5 to 16 s (1,083 actors, 1,350 instances) |
| Picture | `bash shot.sh /project/ue/logs/shots/x.jpg cam=X,Y,Z,pitch,yaw,roll fov=80 frames=60` | about 12 s at 1920 x 1080 with 60 warm-up redraws (fewer leave Lumen unsettled after a camera jump; 60 and 200 give the same picture) |
| The six block views | `bash block-shots.sh` (detached: about 75 s) | |
| Picture to the local checkout | `media_upload` (filename `mi-x.jpg`), `bash put.sh <jpg> <upload_url> image/jpeg`, `media_confirm` (type image), local `curl -o` the url | about 10 s; several thousand tokens per picture |
| Many pictures at once | `tar -cf /tmp/x.tar block-v2-*.jpg` on the box, one `media_upload` (`.tar`, `application/octet-stream`), `put.sh`, `media_confirm` type `file`, local `curl` + `tar -xf`; look at 2 x 2 sheets made locally | 15 pictures, 4.7 MB in one transfer |
| The game through the player's eyes | `bash play-shots.sh [out] [prefix]` (detached; L_Block open): play in editor, `MIStart mission skip`, three poses with the HUD | about 2 minutes |
| Baked interiors | `block.sh start interiors` (then `materials` so the glass instances take the cubes) | 16 s for six rooms |

`mi_mcp.py` is the MCP client: `toolsets [text]`, `describe <Toolset> [Tool]`, `tool <Toolset.Tool> '<json>'`,
`py`, `level`, `shot`. A play-in-editor session left running blocks level queries ("Cannot get the current level
while PIE is active"): `python3 mi_mcp.py tool EditorToolset.EditorAppToolset.StopPIE '{}'`.

## 3. Generated content

Nothing under `unreal/MurderInc/Content/` is committed except `Data/*.json` and `Python/*.py`. Generated content is
rebuilt on the box by committed scripts:

| Content | Script |

## 4. Art transfer (Blender outputs to the box)

The Blender outputs (`art/out/`, git-ignored) travel as one tar through the user's Higgsfield storage:

1. Local: `tools/box/send-art.sh pack` makes `art/out/mi-art-<k>.tar` parts of at most 240 MB (the storage's upload
   front answers 413 above about 500 MB): every `SM_El_*`, `SM_Street_*`, `SM_Facade_*`, `SM_Prop_*`,
   `SM_Gameplay_*`, `SM_Furn_*` GLB (patterns are arguments), every texture set their slots name (BC, N, ORM, E;
   height maps left out), the grey-box sets, `manifest.json` and `placements/*.json`. 611 MB in 3 parts for 190
   meshes and 96 sets; with the structures, signs and vehicles (block-v2) 1,344 MB in 7 parts, 279 GLBs, 222 sets
   (the seven PUTs in parallel about 2 minutes, `receive-art.sh` about 3 minutes).
2. `mcp__Higgsfield__media_upload` with one filename per part (`files` takes several) gives `upload_url`, `url` and
   `media_id` each. The upload address is signed for the headers `content-type` and `if-none-match`: send
   `Content-Type: application/octet-stream` (the type the tool states) and `If-None-Match: *`.
3. Local: `tools/box/send-art.sh put "<upload_url>" application/octet-stream art/out/mi-art-<k>.tar` per part (the
   three in parallel: about 60 s; retries with `If-None-Match: *` on 403).
4. `mcp__Higgsfield__media_confirm` with the `media_ids` and type `file`.
5. Box: `bash receive-art.sh "<url1>" "<url2>" ...` downloads and unpacks all parts to `/project/ue/art-in/` (about
   30 s for 611 MB: start it detached). Several pictures come back the same way as one tar (type `file`): no image
   tokens until a picture is opened.

## 5. GLB import: what turned out to be true

Measured on the first block build (2026-11-22, `build_block.py`, every result line in
`<project>/Saved/BuildBlock/status.txt`):

| Question | Answer |
|---|---|
| Importer | Interchange glTF through `unreal.InterchangeManager.get_interchange_manager_scripted().import_asset(dest, create_source_data(glb), ImportAssetParameters)`; the pipeline is a transient `InterchangeGenericAssetsPipeline` passed as `override_pipelines = [SoftObjectPath(pipeline.get_path_name())]`. Synchronous; returns `(ok, objects)`. |
| Axes | Right as they come. Blender metres (+X east, +Y north, Z up) exported with `export_yup` land as Unreal X east, Y south, Z up, unmirrored: glTF (x, y, z) becomes Unreal (x, z, y) x 100 (`GLTFCore/Private/GLTF/ConversionUtilities.h`), which is Blender (x, -y, z) x 100. No import rotation, no negative scale. |
| Scale | Metres to centimetres by the importer. All 16 meshes match the manifest's `bounds_unreal_cm` to 0.0 cm (e.g. `SM_Street_Kerb_4m` X 0..400, Y -19..0, Z -3.5..15; `SM_El_Deck_10m` X 0..1000, Z 650..778.6). Pivots arrive as authored. |
| Slot names | Kept exactly: the static material slots are named after the Blender materials (`MI_Steel_ScanPaintGreen`, `M_Prop_Hydrant`), so instances are assigned by name. With `material_pipeline.import_materials = False` and `texture_pipeline.import_textures = False` no stray material or texture assets are made. |
| Combine | `mesh_pipeline.combine_static_meshes_behavior = InterchangeCombineStaticMeshesBehavior.ALL` (the old `combine_static_meshes` is deprecated in 5.9 and raises in Python). One GLB gives one `StaticMesh` named after the file (`asset_name`). |
| Nanite | `mesh_pipeline.build_nanite = True`; the 234k-triangle road builds in 19 s. |
| Normal maps | The sets are OpenGL (+Y up). Imported as plain textures (`AssetImportTask`), then `srgb = False`, `compression_settings = TC_NORMALMAP`, `flip_green_channel = True`, `lod_group = TEXTUREGROUP_WORLD_NORMAL_MAP`. ORM: `srgb = False`, `TC_MASKS` (sampler type Masks in the material). |
| Vertex colours (`Wear`, COLOR_0) | Arrive, but the static mesh build stores them sRGB-encoded (`StaticMeshBuilder.cpp`: `LinearColor.ToFColor(true)`) and the vertex factory reads them back raw: the master material decodes RGB with `pow(x, 2.2)`; alpha is stored linearly. Still to prove with a ramp test asset (art bible 3.3). |
| Material graph from Python | `MaterialExpressionCustom` inputs and outputs are built as structs property by property (`CustomInput()` then `set_editor_property`: the constructor takes no keywords). Vector parameters and the vertex colour node give float3 on their main output: alpha comes from the `"A"` output. Never delete a material that instances use: rebuild its graph in place (`delete_all_material_expressions`). |

## 6. Level assembly: what turned out to be true

| Question | Answer |
|---|---|
| Instanced meshes from Python | `SubobjectDataSubsystem.k2_gather_subobject_data_for_instance(actor)[0]` as parent, `add_new_subobject(AddNewSubobjectParams(new_class=InstancedStaticMeshComponent))`, `SubobjectDataBlueprintFunctionLibrary.get_object(get_data(handle))` gives the component; `add_instances(transforms, False, True)` (world space). Saved with the level like a component added in the details panel. One holder actor per building, props, structures and backdrop. |
| Collision | The art carries none (`NO_COLLISION`); every movement-blocking collider of level.json stays a box: visible in a material by tag where no art draws it, hidden (`set_visibility(False)`, no shadow, no distance field) under the art. |
| Glass | Opaque, Nanite, black base, specular 0.5, roughness 0.02: full Lumen reflections; the room behind is emission (110 nits windows, 200 nits shops), so reflections win at grazing angles as on real glass. |
| Alpha cards | A second master `M_MI_SurfaceMasked` (two-sided, opacity mask = BC alpha); the manifest slot's `alpha` key selects it. On the opaque master the chain-link drew as a grey sheet. |
| Decals | Deferred decal material (`MD_DEFERRED_DECAL`, translucent) with the shapes drawn in decal UV by HLSL; DecalActor `decal_size` is (depth, width, height); pitch -90 projects down. |
| Catalogue ids | One table: `Content/Data/art_catalogue.json` (id -> meshes picked by seed, variant overrides, paint slot, parts; `gameplay` ids are drawn by the gameplay actors). |
| Car paint | `M_MI_CarPaint` is the surface master with `MSM_CLEAR_COAT` (CustomData0 = clear coat 1, CustomData1 = its roughness 0.03); one instance per paint slot and props.json colour, set on the instanced component with `set_material_by_name(slot, ...)`. Vehicle sets carry lamp colours in `E`: `EmissiveScale` 0 by day. |
| Vertex colours | Arrive in the shader linear (ramp test `mi_ramp_test.py`: COLOR_0 k/10 reads back k/10 in 8-bit steps through Interchange). No decode in the material. |
| Interiors by cube map | A `SceneCaptureCube` (`SCS_SCENE_COLOR_HDR`) does see direct lights here (only Lumen and the sky light are missing in captures), so small rooms lit by point lights plus a shadowless fill bake well. `RenderingLibrary.render_target_create_static_texture_cube_editor_only(rt, "/Game/...full path", TC_HDR, ...)` makes the asset; a re-bake writes into the existing one with `convert_render_target_to_texture_cube_editor_only`. `capture_scene()` renders on a later tick: capture and save in different build units. |
| LoadLevel in 5.9 | `LevelEditorSubsystem.load_level` refuses while the open map is dirty (picture cameras, play in editor): `load_level(path, unreal.LevelEditorUnsavedChangesPolicy.DISCARD)` (`build_block.load_level`). |
| Gameplay actors and the art | The explosives, reel cases and the IPX truck are spawned at play by the game; their meshes come from `presentation.json` (`explosives.<kind>.mesh`, `objectives.case.art`, `objectives.truck.art`). `build_block.py` places hidden-in-game previews of them so editor pictures show them. |
| Scene capture readback | `RenderingLibrary.read_render_target_raw(world, rt, False)` gives the whole float target as a list (row-major); a capture looking +Y has Unreal +X running to the left of the image. |
